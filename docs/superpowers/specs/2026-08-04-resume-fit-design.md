# Resume Fit 设计规格

- 状态：设计已确认，待用户审阅书面规格
- 日期：2026-08-04
- 目标用户：需要申请中文 AI 产品经理岗位的个人求职者
- 第一版使用范围：个人本地使用，为未来在线公开产品保留清晰的迁移边界
- 第一版运行平台：macOS
- 产品形态：本地网页工具，由 macOS 启动器打开默认浏览器
- 主要语言：中文
- 核心路线：结构化证据工作流

## 1. 执行摘要

Resume Fit 用一条可解释、可恢复的六阶段工作流完成岗位定制简历：

```text
导入并确认 JD
→ 理解岗位
→ 分析匹配
→ 补充证据
→ 生成定制简历
→ 准备面试
```

产品接收粘贴文本或多张招聘平台截图形式的岗位 JD。系统默认在本地完成 OCR、排序、去重和文本合并，用户确认最终 JD 后，系统把招聘话术拆成岗位目标、实际任务、交付物、协作关系、成功指标、显性要求、隐性要求、硬性门槛和风险。

产品维护一份长期可复用的个人档案和项目经历库。经历库保存用户确认过的原子事实，而不是只保存润色后的简历段落。系统把 JD 要求与这些事实逐项匹配，区分强证据、部分证据、有经历但简历未表达、候选证据待确认、信息未知、确认缺口和事实冲突。

系统分别显示“岗位能力适配度”和“当前简历呈现度”。润色可以提高呈现度，但在没有新增真实事实时不能提高能力适配度。对于高价值证据缺口，系统逐项向用户追问；用户确认的新事实可以同步进入经历库。最终简历的每条高风险表达都必须能够追溯到已确认事实。

第一版输出岗位洞察报告、匹配度报告、完整定制简历、修改前后对比、修改依据、Word/PDF 文件和轻量面试准备材料。产品只保留历史生成记录，不记录已投递、面试中或已结束等投递状态，也不展示最近投递项目和待处理追问。

## 2. 已确认的产品决策

| 决策 | 第一版结论 |
|---|---|
| 产品演进 | 先做个人本地版，数据和模块边界为未来公开产品保留迁移空间 |
| 岗位范围 | 中文 AI 产品经理 |
| 核心路线 | 结构化证据工作流，不采用一次性大提示词或多 Agent 自由讨论 |
| 岗位信息来源 | JD、用户补充的公司/业务信息、用户提供的公开网页链接 |
| 简历真实性 | 证据优先；资料不足时追问，不自动补写经历 |
| 项目经历库 | 支持表单、历史简历、项目复盘和零散素材导入 |
| 自动提取 | 所有自动提取事实必须经用户确认后才可用于正式简历 |
| 最终输出 | 完整定制简历、逐条修改依据和轻量面试准备材料 |
| 数据与模型 | 本地存储；云端模型；可选脱敏；保留本地模型适配接口 |
| 模型供应商 | 用户配置接口地址、API Key 和模型名称，不绑定单一供应商 |
| 产品形态 | 本地网页工具，验证后可演进为在线产品 |
| 第一版平台 | 仅 macOS |
| 简历输入 | 纯文本、DOCX、文本型 PDF |
| JD 图片 | 支持一次上传多张 PNG、JPEG 或 WebP |
| 图片识别 | 默认本地 OCR；质量不足时经用户确认调用视觉模型 |
| 数据组织 | 个人档案、项目经历库和历史生成记录 |
| 历史记录 | 保存 JD、岗位分析、匹配、追问、简历版本和面试材料 |
| 投递管理 | 不记录投递状态，不做求职进度管理 |
| 匹配呈现 | 区间总分、分维度得分、证据链、缺口和分析置信度 |
| 语言 | 只支持中文 JD 和中文简历 |
| 导出排版 | 一套固定的单栏 ATS 友好模板，导出 Word 和 PDF |
| MVP 验证 | 使用至少 10 个真实脱敏 AI 产品经理 JD 完成对照测试 |

## 3. 产品目标

### 3.1 核心目标

第一版必须帮助用户完成以下任务：

1. 从文本或多张截图还原完整、可校对的 JD；
2. 解释岗位可能承担的实际工作，而不是复述招聘文案；
3. 从主简历、个人档案和经历库中找出与岗位相关的真实证据；
4. 区分用户真实能力、当前简历表达和信息不足；
5. 用少量高价值追问补齐影响判断与改写的事实；
6. 选择互补的重点项目，生成不编造事实的完整定制简历；
7. 展示每处修改的目的、JD 对应关系和事实来源；
8. 生成与最终简历一致的面试准备材料；
9. 保存历史生成记录和不可覆盖的简历版本；
10. 在本地保存资料，并让用户控制发送给云端模型的内容。

### 3.2 成功标准

第一版同时满足以下条件才算验证成功：

- 使用至少 10 个真实脱敏中文 AI 产品经理 JD 完成全流程测试；
- 岗位分析能区分业务应用型、平台/中台型、模型与评测型、解决方案/交付型、商业化/增长型和内部提效型岗位倾向；
- 关键判断能够追溯到 JD、用户提供的公开资料或用户确认的经历事实；
- 自动生成内容不新增未经用户确认的项目、职责、方法、数字或结果；
- 用户认为至少 80% 的最终文案可以直接采用或只需轻微修改；
- 相比完全手工分析和修改，每个 JD 平均节省至少 30 分钟；
- Word 和 PDF 导出无明显字体、分页、空白页或内容缺失问题；
- macOS 可以一键启动、退出后恢复、备份并删除本地数据。

### 3.3 第一版非目标

第一版明确不做：

- 多用户账号、登录、权限和云端同步；
- 付费、套餐、订单和运营后台；
- 招聘平台账号连接或岗位自动同步；
- 投递状态、面试日程、提醒和求职漏斗；
- 首页的最近投递项目和待处理追问；
- 全网自动搜索公司和岗位；
- 绕过招聘平台登录、验证码、付费墙或反爬限制；
- 英文 JD、英文简历和中英文互译；
- Windows 和移动端原生应用；
- 扫描 PDF OCR；
- 任意 Word 原简历版式还原；
- 复杂表格、流程图和嵌入附件的深度解析；
- 语音模拟面试、摄像头分析和实时面试评分；
- 多 Agent 自由讨论；
- 向量数据库、知识库和模型微调；
- 完全本地大模型运行；
- 对 ATS 通过、面试邀请或录用结果作保证。

│   └── 主简历

│   ├── 待确认导入内容

主入口突出“新建一次简历生成”，不展示最近任务、待办事项或求职进度。历史生成记录是被动查询入口，用户需要时再打开。

六个阶段只是一次生成流程的内部步骤，不对应投递状态。退出过程中自动保存草稿，再次打开可以从中断步骤继续。完成后可以重新查看、复制、导出或基于同一 JD 生成新版本。

## 5. 六阶段工作流

### 5.1 导入并确认 JD

用户可以粘贴 JD、上传多张截图、填写公司/业务信息和提供公开网页链接。系统完成 OCR、排序、去重、结构恢复和人工校对。只有用户确认后的 JD 才能进入分析。

### 5.2 理解岗位

系统拆解岗位目标、明确职责、硬性门槛、核心要求、加分项、协作关系、交付物、成功指标和信息缺口，并给出岗位类型倾向和实际工作内容推断。事实与推断必须明确分开。

### 5.3 分析匹配

系统把岗位要求与主简历、个人档案和项目经历库逐项匹配，分别计算岗位能力适配度和当前简历呈现度，显示证据、缺口和置信度。

### 5.4 补充证据

系统针对最影响判断和简历选择的信息逐项追问。用户可以回答、跳过、确认没有经历或结束追问。确认后的新事实可以同步到项目经历库。

### 5.5 生成定制简历

系统先提出项目组合与改写策略，再生成完整简历、逐段差异和事实引用。用户可以接受、拒绝或编辑单段内容，每次完整生成都创建新版本。

### 5.6 准备面试

系统根据最终 JD、最终简历和已确认事实生成岗位重点、自我介绍、项目深挖、专业问题、风险问题和反向提问。面试材料是可跳过的轻量增强，不阻塞简历导出。

## 6. JD 导入与确认

### 6.1 支持输入

| 输入 | 第一版处理 |
|---|---|
| 粘贴文本 | 直接进入区块识别和校对 |
| 多张截图 | 本地 OCR、排序、去重、合并和校对 |
| 公司与业务信息 | 作为用户提供的岗位背景 |
| 公开网页链接 | 抓取无需登录的静态正文并等待确认 |

JD 图片支持 `.png`、`.jpg`、`.jpeg` 和 `.webp`。一次最多 20 张，单张不超过 15 MB。

### 6.2 多图处理

```text
选择或拖入图片
→ 生成缩略图
→ 用户排序、旋转或删除
→ 本地 OCR
→ 检测相邻截图重叠
→ 合并并去重
→ 识别标题、职责和要求区块
→ 用户检查和修正
→ 确认最终 JD
```

系统保留文字与原图位置的对应关系。点击识别文字时可以查看来源截图和文本框。

以下情况必须提示用户，不允许静默猜测：

- 图片模糊或字号过小；
- 截图顺序无法判断；
- 内容被悬浮元素遮挡；
- 截图开头或结尾可能缺失；
- 多张截图存在大量重叠；
- 关键数字、英文术语或标点置信度低；
- OCR 结果与招聘页面视觉结构明显不一致。

本地 OCR 质量不足时，用户可以选择指定图片并确认发送给视觉模型。没有视觉模型或用户拒绝发送时，流程退回人工校对，不阻塞文本分析。

## 7. 岗位拆解与实际工作推断

### 7.1 信息层级

每条关键结论必须属于以下类型之一：

- JD 明确事实；
- 用户补充事实；
- 公开来源支持的事实；
- 根据岗位模式得出的推断；
- 信息不足、无法判断。

系统不能把推断写成公司内部事实。

### 7.2 JD 结构

| 维度 | 内容 |
|---|---|
| 岗位基本信息 | 公司、部门、岗位、地点和职级线索 |
| 岗位目标 | 招聘该角色可能要解决的问题 |
| 明确职责 | JD 直接描述的任务和交付物 |
| 硬性门槛 | 明确且可能直接筛选的条件 |
| 核心要求 | 完成主要工作必须具备的能力 |
| 重要要求 | 明确需要但不是唯一重点的能力 |
| 加分项 | 优先、熟悉或有经验更佳的条件 |
| 产品对象 | 消费者、企业客户、内部员工或开发者 |
| AI 对象 | 大模型应用、RAG、Agent、平台、数据或评测 |
| 产品阶段 | 探索、从 0 到 1、规模化、商业化或交付 |
| 协作角色 | 算法、工程、数据、设计、业务、销售或客户 |
| 成功指标 | 产品、模型、业务、成本和交付指标 |
| 不确定项 | 缺失、矛盾或只有口号的信息 |

### 7.3 岗位类型

系统采用多标签倾向，不强制把岗位归入唯一类别：

- 业务应用型；
- 平台/中台型；
- 模型与评测型；
- 解决方案与交付型；
- 商业化/增长型；
- 内部提效型。

比例只用于解释岗位重心，不代表科学测量。

### 7.4 岗位洞察输出

岗位洞察报告包含：

- 一句话岗位定位；
- 岗位存在的可能原因；
- 岗位类型倾向；
- 高频实际任务；
- 主要交付物；
- 真实协作关系；
- 可能承担的成功指标；
- 显性要求和隐性要求；
- 硬性门槛；
- 岗位边界和风险；
- 面试重点；
- 每项关键结论的依据、类型和置信度；
- 仍需确认的问题。

统一结论格式：

```text
结论：岗位可能需要建立大模型功能的评测和迭代闭环
类型：推断
置信度：较高
依据：
- JD 要求“制定评测标准”
- JD 要求“推动算法效果持续优化”
- 用户提供的产品资料显示产品已经进入规模化使用
仍需确认：
- 是否已有固定评测集
- 岗位是否亲自负责数据标注和实验分析
```

用户修改或确认岗位洞察后，系统才进入匹配阶段。

## 8. 项目经历库

### 8.1 基本原则

项目经历库保存可复用、可确认的真实事实，不把生成文案当成事实：

```text
项目事实层
→ 根据目标 JD 选择事实
→ 生成本次简历表达
→ 保存为历史版本
```

生成文案不能自动覆盖项目事实。用户在简历编辑器里修改一句话，也不能自动改变经历库。

### 8.2 项目结构

| 模块 | 内容 |
|---|---|
| 基本信息 | 项目名称、所属公司、时间和项目状态 |
| 项目背景 | 业务背景、用户、原有问题和立项原因 |
| 项目目标 | 目标和衡量方式 |
| 个人定位 | 职位、负责范围、决策权和团队规模 |
| 关键动作 | 调研、规划、设计、验证、推进、上线和复盘 |
| AI 方案 | 模型、RAG、Agent、Prompt 或工作流 |
| 数据与评测 | 数据来源、测试集、指标、人工评测和实验方法 |
| 协作关系 | 算法、研发、设计、业务、销售和客户 |
| 难点与取舍 | 数据、效果、成本、延迟、安全和组织限制 |
| 项目结果 | 产品、模型、业务、效率、成本或交付结果 |
| 复盘结论 | 成功、失败、后续迭代和个人收获 |
| 能力标签 | 产品规划、AI 理解、评测、商业化、交付等 |
| 敏感性 | 公司名、客户名、内部指标和允许公开范围 |

AI 产品经理项目按需追问：

- 为什么该场景适合 AI；
- 用户原流程和痛点；
- 使用了哪类模型能力；
- 产品、算法和研发各自负责什么；
- 如何定义效果；
- 是否建立测试集、评测指标和验收标准；
- 如何处理幻觉、准确率、延迟、成本、安全和异常；
- 如何收集反馈并推动迭代；
- 最终产生什么结果；
- 哪些数字可以公开。

### 8.3 导入方式

第一版支持：

1. 结构化表单录入；
2. 从主简历或历史简历拆分候选项目；
3. 从项目复盘、工作笔记和粘贴素材提取候选项目。

简历和素材支持纯文本、DOCX 和文本型 PDF。系统将长段材料拆成原子事实，并保留来源原文和位置。

### 8.4 事实状态

每条原子事实只能处于以下状态之一：

- 待确认；
- 用户已确认；
- 已拒绝；
- 存在冲突；
- 已归档。

模型提取的待确认事实不能用于正式简历。对于个人工具，“用户已确认”就是可用的真实性标准；产品不要求上传证明，也不声称执行背景调查。

每条事实记录来源、原文、所属项目、确认时间、修改时间、敏感性和允许公开范围。用户可以保存真实精确值，同时只允许简历使用相对变化或模糊区间。

### 8.5 项目完整度

每个项目显示素材完整度，而不是项目质量评分：

```text
背景：完整
目标：完整
个人职责：部分缺失
关键动作：完整
AI 方案：完整
评测方法：缺失
量化结果：部分缺失
```

字段缺失不阻止用户使用项目。没有公开数字时，可以使用用户规模、覆盖场景、交付范围或定性结果。

### 8.6 检索与推荐

第一版采用结构化字段、能力标签、全文检索和模型相关性排序，不使用向量数据库。项目推荐考虑：

- 是否覆盖硬性门槛和核心要求；
- 个人贡献是否清晰；
- 是否有可验证结果；
- 是否接近岗位场景；
- 是否与其他项目重复；
- 是否包含无法公开或证据不足的内容。

通常推荐两至四个互补项目，分别证明业务理解、AI 产品能力、数据评测、落地推进和业务结果。

## 9. 匹配度与证据追问

### 9.1 双指标

系统分别显示：

```text
岗位能力适配度：真实经历与岗位要求的匹配程度
当前简历呈现度：当前简历是否清楚展示这些能力
```

示例：

```text
岗位能力适配度：72–79
当前简历呈现度：51–58
分析置信度：中等
```

如果没有新增真实事实，简历润色只能提高呈现度，不能提高能力适配度。

### 9.2 匹配维度

第一版包括：

1. 业务与用户理解；
2. 产品规划与产品基本功；
3. AI 场景和方案设计；
4. 模型、RAG、Agent 等技术理解；
5. 数据、评测与效果迭代；
6. 跨团队推进与项目落地；
7. 业务结果与商业化；
8. 行业与岗位特定经验。

权重根据本次 JD 调整，不固定平均。用户可以查看并修正要求的重要性。

### 9.3 证据状态

- 强证据：已确认事实直接证明能力，职责和结果清晰；
- 部分证据：有相关经历，但范围、深度、职责或结果不足；
- 有经历但简历未表达：经历库有证据，当前简历没有体现；
- 候选证据待确认：材料中可能存在，但用户尚未确认；
- 信息未知：资料不足，无法判断；
- 确认缺口：用户确认没有相关经历；
- 存在冲突：简历、经历库或用户回答不一致。

“信息未知”不能自动计为不匹配，“有经历但未表达”不能计为能力缺口。

### 9.4 评分

评分由确定性规则和模型证据判断共同完成。

确定性规则负责：

- 要求的重要性；
- 证据状态对应的分值区间；
- 维度汇总；
- 硬性门槛单独提示；
- 信息未知造成的区间宽度；
- 最终结果的一致计算。

模型负责：

- 识别 JD 要求；
- 判断事实与要求的相关性；
- 解释证据强弱；
- 发现事实是否被过度解读。

评分只显示整数区间，不显示小数。硬性门槛不被综合分平均掉：

```text
综合适配度：70–77
硬性门槛风险：工作年限可能不满足
```

随着用户确认 JD、补充事实和回答问题，区间应逐步收窄。

### 9.5 追问优先级

追问优先级由以下因素共同决定：

```text
要求重要性
× 对匹配判断的影响
× 经历库存在相关线索的概率
× 用户回答成本
```

系统一次只展示一个主要问题，支持“有，继续补充”“没有相关经历”“不确定”“暂时跳过”和“结束追问并生成”。默认建议回答 5–10 个高价值问题，但不强制建立完整档案。

问题必须是事实型问题。例如先询问是否建立过固定测试集，再根据回答追问规模、覆盖场景、指标、职责和结果；不能在问题中暗示用户具有某个经历或某个提升数字。

用户回答先保存在本次记录中。系统拆分出候选原子事实，经用户确认后才同步到项目经历库。

### 9.6 匹配报告

匹配报告包含：

- 能力适配度区间；
- 当前简历呈现度区间；
- 分维度匹配；
- 硬性门槛风险；
- 最强证据；
- 有经历但没有表达的能力；
- 证据不足项；
- 用户确认的真实缺口；
- 推荐追问；
- 推荐采用的项目；
- 不建议声称的内容；
- 分数变化原因。

匹配度不代表 ATS 通过概率、面试概率、录用概率或公司的真实内部权重。

## 10. 简历生成

### 10.1 两段式生成

```text
岗位要求与证据矩阵
→ 推荐项目组合
→ 制定保留、强化、弱化和删除策略
→ 用户调整项目选择
→ 生成完整简历
→ 事实和关键词校验
→ 修改前后对比
→ 编辑、生成新版本或导出
```

### 10.2 可调整内容

第一版可以调整：

- 职业摘要；
- 核心技能；
- 工作经历中的职责与成果；
- 项目经历的选择、顺序、标题和要点；
- 与岗位相关且有事实支持的关键词；
- 项目要点的篇幅和表达重点。

模型默认不能修改：

- 姓名和联系方式；
- 公司名称；
- 任职时间；
- 正式职位名称；
- 学校、学历和毕业时间；
- 用户已确认的数字；
- 证书名称和时间。

系统可以提示问题，但不能自行修正上述事实。

### 10.3 项目组合

每个候选项目显示关联要求、可证明能力、证据强度、重复度、个人贡献、量化结果、敏感性和推荐理由。用户可以接受推荐、加入或移除项目、调整顺序、指定必须保留或禁止使用，以及选择脱敏表达。

项目组合优先覆盖互补能力，不选择一组只能重复证明同一能力的项目。

### 10.4 改写规则

每个项目要点优先采用：

```text
行动或决策
+ 解决的问题
+ 使用的方法
+ 个人负责范围
+ 可验证结果
```

不要求机械套用完整 STAR。系统不能：

- 把参与写成主导；
- 把团队能力写成个人能力；
- 把原型或试验写成正式上线；
- 把普通 FAQ 配置写成 RAG；
- 把算法协作写成亲自训练模型；
- 改变数字口径；
- 使用没有事实支撑的 JD 关键词；
- 为填满版面增加未经确认的内容。

### 10.5 完整简历结构

固定模板包含：

1. 姓名和联系方式；
2. 求职方向；
3. 职业摘要；
4. 核心能力；
5. 工作经历；
6. 重点项目经历；
7. 教育经历；
8. 可选证书或补充信息。

默认生成两页以内的中文简历。内容溢出时，系统优先删除重复表达、压缩低相关经历和减少低价值要点，同时保留工作时间连续性和基本任职信息。

### 10.6 修改对比与依据

编辑器提供：

- 完整简历；
- 改写前后逐段对比；
- 按 JD 要求查看证据覆盖。

每处模型修改显示修改目的、引用事实、对应 JD 和风险提示。用户可以接受、拒绝或编辑单段，不要求整份重新生成。

### 10.7 事实校验

完整简历生成后检查：

- 数字是否来自已确认事实；
- 强动词是否有职责依据；
- 技术术语是否与真实方案一致；
- 时间线是否冲突；
- 结果是否重复使用；
- 是否引入不存在的新事实；
- 是否泄露敏感信息；
- 最终简历与面试材料是否一致。

发现问题时必须标记具体句子，并提供“修改表述”“补充事实”或“删除内容”，不能静默通过。

### 10.8 版本

每次完整生成创建不可覆盖的新版本。版本支持自动保存、自定义名称、查看模型和时间、任意版本比较、恢复为新版本、删除和标记当前定稿。

历史生成记录保留版本，但不包含投递状态。

### 10.9 导出

第一版使用一套 A4、单栏、ATS 友好的模板：

- 使用中文常用字体；
- 使用标准标题；
- 不使用文本框、复杂表格、图标化技能条或多栏布局；
- 不把关键信息放在页眉页脚；
- Word 和 PDF 使用同一份规范化内容；
- 正式简历不显示内部评分、事实编号和修改依据。

导出前检查页数、字体、分页、空白页、链接和机器文本提取。文件名使用安全格式，例如 `姓名_AI产品经理_公司名_20260804.docx`。

## 11. 面试准备材料

面试材料只基于最终岗位洞察、最终简历和已确认事实，包含：

1. 三至五项岗位面试重点；
2. 60 秒自我介绍提纲和参考版本；
3. 重点项目深挖问题；
4. AI 产品专业问题；
5. 硬性门槛、薄弱项和职责边界问题；
6. 行为与协作问题；
7. 向面试官确认岗位真实范围的反向问题。

第一版默认生成约 12–18 个高价值问题，分为“高概率必准备”“建议准备”和“补充准备”。

每个问题包含：

- 问题；
- 为什么可能被问；
- 可以引用的已确认事实；
- 建议回答结构；
- 仍需核实的信息。

系统提供回答结构，但不补写经历。用户确认没有某项经历时，系统只建议诚实说明边界、使用可迁移能力或说明学习计划。

面试材料检查数字、职责、项目时间和敏感性是否与最终简历一致。简历修改后，旧面试材料标记为基于旧版本，用户决定是否重新生成。

工具内支持问题卡片、优先级筛选、个人笔记、复制和导出 Markdown/PDF，不发展成长期面试任务管理器。

## 12. 技术架构

### 12.1 总体结构

```text
Resume Fit.app
│
├── macOS 启动器
│   ├── 启动本地服务
│   ├── 检查数据库
│   ├── 选择本地端口
│   └── 打开默认浏览器
│
├── React + TypeScript 前端
│
├── Python + FastAPI 本地服务
│   ├── 文档解析
│   ├── OCR 与图片合并
│   ├── 确定性工作流
│   ├── 模型适配器
│   ├── 证据与评分引擎
│   ├── 文档生成
│   └── 历史记录管理
│
├── SQLite + FTS5 + 本地文件
│
└── 外部服务
    ├── 用户配置的文本模型 API
    ├── 可选视觉模型 API
    └── 用户提供的公开网页
```

FastAPI 可以提供 API 和编译后的静态前端，也支持把处理任务与初始请求分离，适合作为单用户本地服务边界。第一版使用持久化任务记录和本地工作线程，避免仅依赖易丢失的临时后台任务。[FastAPI 静态文件文档](https://fastapi.tiangolo.com/tutorial/static-files/)、[FastAPI 后台任务文档](https://fastapi.tiangolo.com/tutorial/background-tasks/)

本地服务只监听 `127.0.0.1`，启动时生成随机会话令牌，不向局域网开放。已有实例运行时，启动器直接打开现有页面。

### 12.2 模块边界

| 模块 | 职责 | 不负责 |
|---|---|---|
| 导入 | 文件接收和文本提取 | 岗位判断 |
| OCR | 图片识别、坐标和重叠检测 | 补全缺失内容 |
| JD | 结构化 JD 和岗位洞察 | 修改个人事实 |
| 经历库 | 项目、原子事实、确认和冲突 | 生成定制文案 |
| 匹配 | 要求、证据、权重和区间评分 | 修改事实 |
| 追问 | 高价值问题和用户回答 | 诱导补写经历 |
| 简历 | 项目选择、改写、差异和校验 | 覆盖经历库 |
| 面试 | 最终简历对应的准备材料 | 长期面试流程 |
| 导出 | DOCX、打印版 PDF 和报告 | 修改内容 |
| 模型 | 供应商适配、调用和用量 | 决定产品流程 |
| 隐私 | 脱敏、发送预览和敏感策略 | 改写原事实 |

第一版不使用 Docker、Redis、PostgreSQL、Celery、LangGraph、向量数据库和多 Agent 自由讨论。

### 12.3 核心实体

```text
Workspace
├── Profile
├── MasterResume
├── Project
│   └── AtomicFact
├── ImportedSource
├── GenerationRecord
│   ├── JDSource
│   ├── ConfirmedJD
│   ├── ResearchSource
│   ├── JobInsight
│   ├── JobRequirement
│   ├── EvidenceMatch
│   ├── ClarifyingQuestion
│   ├── UserAnswer
│   ├── ResumeStrategy
│   ├── ResumeVersion
│   └── InterviewPack
└── ModelCallRecord
```

`GenerationRecord` 是历史生成记录，不是投递项目。每个主要实体保存 UUID、时间、版本、来源、确认状态、所属工作区和归档标记。

第一版只有一个本地工作区，但实体保留 `workspace_id`，方便未来增加账号和多租户，而不要求第一版实现权限系统。

SQLite FTS5 用于项目事实和导入材料的全文检索。中文检索质量必须用真实样本验证，并与结构化标签、字段过滤和模型排序组合使用。[SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)

### 12.4 本地文件

应用数据保存在 macOS 用户应用数据目录：

```text
Resume Fit/
├── resumefit.sqlite3
├── imports/
├── jd-images/
├── exports/
├── backups/
└── logs/
```

数据库保存结构化数据和文件元数据，原始文件作为普通文件保存。磁盘文件使用 UUID 命名，界面显示原始文件名。

默认限制：

- 单个简历文件不超过 20 MB；
- PDF 不超过 20 页；
- 一次 JD 图片最多 20 张；
- 单张图片不超过 15 MB；
- 一次零散素材不超过 50 MB；
- 扫描 PDF 明确提示不支持，不返回空内容。

### 12.5 OCR

OCR 使用可替换适配器，默认采用 RapidOCR 的 ONNX Runtime 路线。官方文档提供 ONNX Runtime 安装方式和中文识别模型；具体模型版本由实现阶段的招聘截图基准测试决定。[RapidOCR 安装文档](https://rapidai.github.io/RapidOCRDocs/main/install_usage/rapidocr/install/)、[RapidOCR 模型列表](https://rapidai.github.io/RapidOCRDocs/latest/model_list/)

OCR 保存原始文字、用户修正文字、图片编号、文本框坐标和置信度。图片感知哈希检测重复图，相邻 OCR 首尾文本检测连续截图重叠。系统只提出自动去重建议，低置信度内容由用户确认。

### 12.6 文档

导入范围：

- DOCX 正文段落和简单表格；
- 文本型 PDF 的文本和页码；
- 纯文本；
- 不解析 Word 复杂图形、嵌入附件和浮动文本框；
- 扫描 PDF 改用截图或粘贴文本。

导出先生成格式无关的 `ResumeDocument`，再分别渲染固定 DOCX 模板和 HTML 打印页。PDF 由随应用打包的 Chromium/Playwright 打印管线生成，用户不需要手动操作系统打印对话框。Playwright 的 `page.pdf()` 可以按照打印 CSS 和 A4 页面参数返回 PDF，因此同一套 HTML 既可用于工具内预览，也可用于确定性导出。[Playwright PDF 官方文档](https://playwright.dev/docs/api/class-page#page-pdf)

随应用打包 Chromium 会增大安装包，但第一版优先保证 PDF 可以直接导出、自动检查和稳定复现。DOCX 和 PDF 使用同一个内容对象，文案不会分别生成。

`python-docx` 支持创建和更新 DOCX，并能利用模板样式生成段落、标题和列表，适合固定模板而不是任意版式还原。[python-docx 官方文档](https://python-docx.readthedocs.io/en/latest/user/documents.html)

导出后重新读取 DOCX，检查关键文本、页数、空白页、标题孤行、字体回退、联系方式和 DOCX/PDF 规范化文本一致性。

## 13. 模型调用

### 13.1 配置

用户填写：

- API 接口地址；
- API Key；
- 文本模型名称；
- 可选视觉模型名称；
- 接口协议类型；
- 是否支持图片；
- 是否支持结构化输出；
- 超时时间；
- 单次任务最大调用次数；
- 可选 Token 或费用提醒。

API Key 存入 macOS Keychain，数据库只保存引用。备份包不包含 API Key。

### 13.2 能力测试

兼容接口必须经过：

```text
网络连通
→ 身份验证
→ 简短文本生成
→ 结构化 JSON 测试
→ 可选图片测试
→ 展示实际能力
```

系统不能假设所有兼容供应商都支持完全相同的结构化输出或视觉能力。

### 13.3 结构化输出

模型任务使用版本化提示词和 Schema：

```text
模型返回
→ JSON 解析
→ 字段和枚举校验
→ 事实引用校验
→ 允许一次定向修复
→ 仍失败则停止并允许用户重试
```

不合法输出不能强行进入后续流程。

### 13.4 调用记录

每次调用保存供应商、模型、时间、任务类型、提示词版本、输入摘要哈希、Token 用量、费用信息、结果状态和重试情况。

日志不记录 API Key，默认不记录完整简历正文。一个模型失败后不自动把资料发送给另一供应商。更换供应商必须由用户决定。

## 14. 工作流、版本与恢复

内部产物状态：

```text
JD_CONFIRMED
→ JOB_INSIGHT_CONFIRMED
→ MATCH_READY
→ EVIDENCE_CONFIRMED_OR_SKIPPED
→ RESUME_GENERATED
→ INTERVIEW_PACK_OPTIONAL
```

这些是内部依赖状态，不是投递状态，不在首页作为待办展示。

每一步保存输入快照、结构化输出、用户修改、模型和提示词版本、上一步依赖版本。

修改已确认 JD 后：

- 旧岗位洞察保留；
- 匹配、简历和面试材料标记为基于旧 JD；
- 用户决定是否重新生成；
- 系统不自动产生新模型费用。

耗时任务支持进度、取消和重试。关闭浏览器不删除任务。第一版一次只运行一个主要生成任务，避免并发写入和意外模型费用。

## 15. 联网调研

第一版联网范围：

- 用户主动填写公司、产品和业务信息；
- 用户提供一个或多个公开网页；
- 系统读取无需登录的静态正文；
- 用户确认提取内容后才用于分析。

第一版不内置全网搜索引擎，不自动搜索公司。动态页面无法读取时，要求用户粘贴文字或上传截图。

网页内容作为不可信资料处理：

- 只允许 HTTP 和 HTTPS；
- 拦截本机、局域网和私有地址；
- 限制响应大小和跳转次数；
- 不下载可执行文件；
- 网页里的指令性文本不影响系统规则；
- 保存 URL、标题和抓取时间。

## 16. 隐私与安全

### 16.1 发送预览

调用模型前展示本次发送内容：

```text
发送：
- 已确认 JD
- 用户选择的项目事实
- 当前任务需要的简历片段

不发送：
- 与任务无关的项目
- 原始文件二进制内容
- API Key
- 本地路径
- 用户排除的敏感字段
```

### 16.2 脱敏

支持公司名、客户名、姓名、联系方式、内部产品名、精确业务数字和自定义关键词。替换映射只保存在本地。模型返回后，占位符只有在完整且上下文明确时才恢复。

### 16.3 安全边界

第一版向用户明确说明：

- 原始资料和结构化数据保存在本地；
- API Key 保存在系统钥匙串；
- 用户调用模型时，发送预览中的内容会到达其配置的供应商；
- SQLite 和原始文件默认不做应用层加密；
- 本地数据安全依赖 macOS 账号、磁盘加密和设备安全；
- 用户可以删除全部数据并创建不含 API Key 的备份包。

文件导入检查大小、扩展名、MIME、路径和解压风险。网页抓取阻止私有地址，降低 SSRF 风险。外部文本和 JD 都视为数据，不能覆盖系统指令。

## 17. 异常处理

| 异常 | 行为 |
|---|---|
| 图片模糊 | 标出低置信度区域，要求校对或确认视觉模型 |
| JD 截图不完整 | 提示可能缺失，不补写 |
| PDF 提取为空 | 判定可能为扫描 PDF，停止分析 |
| DOCX 结构复杂 | 显示已提取内容和可能遗漏项 |
| 模型连接失败 | 保留任务，允许测试设置和重试 |
| 模型超时 | 不无限重试，说明再次调用可能收费 |
| JSON 不合法 | 定向修复一次，仍失败则停止 |
| 模型引用不存在事实 | 阻止该段进入正式简历 |
| 网页无法访问 | 保留 URL，允许粘贴或截图 |
| 磁盘空间不足 | 停止新写入，不破坏已有记录 |
| 应用意外关闭 | 从最后一个保存产物恢复 |
| 导出超过两页 | 标出溢出并建议压缩 |
| Word/PDF 不一致 | 阻止标记为正式导出 |

每条错误信息必须说明失败步骤、已经保存的内容、是否产生模型调用、恢复方式和重试费用风险。

## 18. 测试方案

### 18.1 单元测试

- OCR 文本重叠与去重；
- JD 要求权重；
- 证据状态映射；
- 区间评分；
- 硬性门槛提示；
- 原子事实确认和冲突；
- 脱敏与占位符恢复；
- 版本依赖和过期标记；
- 文件名和路径安全。

### 18.2 模型契约测试

使用固定输入和模拟响应验证：

- Schema 校验；
- 缺失字段和非法枚举；
- 伪造事实引用；
- Prompt 注入资料；
- 超时和限流；
- 结构化输出差异；
- 视觉模型不可用时的降级。

自动测试不依赖真实付费 API，只保留少量人工触发的真实模型冒烟测试。

### 18.3 集成测试

```text
多张 JD 截图
→ OCR 与人工修正
→ 岗位洞察
→ 导入简历和项目
→ 匹配分析
→ 回答证据问题
→ 生成简历
→ 事实校验

```

### 18.4 浏览器端到端测试

覆盖文件上传、图片排序、页面刷新恢复、接受或拒绝改写、版本比较、任务取消、模型设置、历史记录、备份和恢复。

### 18.5 人工质量基准

至少 10 个真实脱敏中文 AI 产品经理 JD，覆盖业务应用、平台/中台、模型与评测、解决方案/交付、商业化/增长和内部提效。

人工检查：

- 是否解释岗位而不是复述 JD；
- 岗位类型和工作推断是否合理；
- 重要要求是否遗漏；
- 是否正确区分证据与缺口；
- 是否出现未经确认的事实；
- 推荐项目是否覆盖核心能力；
- 文案是否自然、具体和可投递；
- 面试材料是否与简历一致；
- Word/PDF 是否完整可读。

## 20. 未来演进边界

第一版通过以下边界为在线产品保留升级空间，但不提前实现空壳功能：

- 业务实体带 `workspace_id`，未来可以增加用户归属；
- 模型、OCR、文件存储和网页读取使用适配器接口；
- 领域服务不直接依赖 macOS 文件路径；
- 前端通过 API 使用后端能力；
- 本地 SQLite 仓库可以替换为云端数据库仓库；
- 本地文件存储可以替换为对象存储；
- Keychain 密钥提供者可以替换为服务端密钥管理；
- 历史生成记录保持与投递状态无关，未来如需招聘管理应作为独立模块设计。

未来候选能力包括 Windows、英文简历、在线账号、云端同步、可配置模板、全网检索、语音模拟面试和本地模型。它们都不进入第一版实施计划。

## 21. 设计原则总结

Resume Fit 的核心不是“把简历写得更像 JD”，而是：

```text
还原岗位真实重心
→ 找到用户真实经历中的最佳证据
→ 补齐影响判断的事实
→ 用可追溯、可校验的方式重新组织表达
```

任何生成质量都不能以牺牲真实性、可解释性和用户控制为代价。
